# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This is a **content repository** for daily news briefings ("Morning Download") as standalone Markdown files. A small Node script generates the website's JSON feed; most work here means authoring and editing Markdown.

Each briefing covers two beats: (1) world events / markets / M&A, and (2) AI and agentic systems. Briefings are generated by a scheduled "Daily News Brief" task and committed via PR.

## Layout

- `briefs/YYYY-MM/YYYY-MM-DD.md` — one file per day, grouped into month subfolders (e.g. `briefs/2026-06/2026-06-15.md`).
- `briefs/YYYY-MM/YYYY-MM-DD-evening.md` — optional additional editions for a given day (suffix the edition name).

## Briefing format

The format has evolved; follow the conventions below and use `briefs/2026-10/2026-10-21.md` as the per-story citation example. The current convention:

- Title: `# Morning Download — Month D, YYYY`, with `---` horizontal rules separating major blocks.
- `## Section 1: World & Market Briefing` — each item is a bolded headline prefixed with a topical emoji (🇪🇺 🏛️ 📊 🏦 💼), followed by analysis. Include one item explicitly marked **Wildcard**.
- `## Section 2: AI & Agentic Systems Briefing` — same emoji-headline format (🧠 🔮 🤖 🔌 📊 💡).
- Immediately after each story in either section (including Wildcards), add a separate paragraph beginning with plain `Sources:`. Use short publisher labels and separate multiple Markdown links with ` · `, for example `Sources: [Publisher](https://example.com/article) · [SEC](https://www.sec.gov/Archives/...)`. Leave a blank line before and after it. Do not bold the label, put it in a bullet, or embed it in the story's body.
- `## Closing` — bundles two bold inline items: `**Sleeper Story:**` (one under-covered story with a "why it matters" argument) and `**One-Liner:**` (a single synthesizing sentence summarizing the day).
- `## Sources` — retain the complete bulleted list of `[Title — Publisher](url)` links backing the claims. Every per-story URL must also appear here, exactly matching the URL and listed once. The short labels beside stories supplement this full bibliography.

This `## Closing` block is the prevailing recent convention (e.g. `briefs/2026-05-22.md` through `briefs/2026-05-28.md`). One brief (`briefs/2026-05-29.md`) instead split Closing into standalone `## Sleeper Story` and `## One-Liner` headers — that's a one-off variation, not the norm; default to the `## Closing` form.

Each headline's body is analysis-forward: state the fact, then explain the second-order implication (often addressed to enterprise/builder readers). Older briefs (`briefs/2026-04-*.md`) used plain bullet lists with inline `**Why it matters:**` tags rather than the emoji-prefixed headlines — do not copy that bullet style for new entries.

## Working conventions

- Dates in this repo are in 2026 (the news content is dated accordingly); do not "correct" them to the present.
- Sources should be real, working URLs that substantiate the headlines — every factual claim in a briefing should be traceable to the Sources list.
- Map citations while researching each story. Link only articles that support that story's claims and figures; do not infer associations from source-list order or repeat every source under every story. The Closing can synthesize already-cited stories; any new factual claim there also needs support in the full Sources list.
- One briefing per file; never edit a prior day's briefing to add a new day.
- **Check the repo before calling anything upcoming.** Before writing that an event is planned, pending, expected, or "eyeing" something — an IPO, a launch, a ruling, a deadline, a spec release — grep `briefs/` for the subject and confirm it has not already happened in an earlier briefing. Stale pre-event coverage outranks post-event coverage in search results for weeks afterward, so a source saying "X is planning Y" is not evidence that Y hasn't already occurred. A completed event written up as forthcoming is the most damaging error this briefing can make.
- **Every named figure needs a source in the same briefing.** Valuations, prices, percentages, dates and vote counts must each be traceable to an entry in that day's `## Sources` list. If no source substantiates a number, cut the number — do not carry it because it appeared in a prior draft or a roundup page.
- Prefer a dated, article-level URL over a homepage, index, or rolling "this week" feed. Rotating pages stop substantiating the claim as soon as they update.
- **Sanity-check dates against the calendar.** A market open, close, session high/low or trading-volume figure must fall on a weekday the exchange was open; a weekday label attached to a date must match that date. Aggregators and search summaries routinely round a Monday session back to the weekend. Check the date before you print it — a precise but impossible date reads as authoritative and is harder to catch than a vague one.

## Feed validation and preview

- Run `node --test .github/scripts/generate-site-feed.test.mjs` when changing the feed parser, then `node .github/scripts/generate-site-feed.mjs` to regenerate `site/briefs.json` on your working branch.
- Each cited story gains an optional `sources: [{ label, url }]` array. Historical stories without a citation paragraph keep their existing shape. The full briefing-level `sources` array stays available.
- The generator rejects malformed or orphaned citation paragraphs and per-story links absent from that briefing's full Sources list. It checks structure, not whether an article substantiates a claim; authors must verify the content.
- An optional output path (`node .github/scripts/generate-site-feed.mjs /absolute/path/briefs.json`) supports a local site preview. Generating a file does not publish it. Keep preview work on a feature branch; do not merge or deploy until requested.

## Required PR review handoff

- Codex automatically reviews the initial PR head, but a correction push does not automatically start a follow-up review. Immediately after pushing any correction commit, comment exactly `@codex review` on that PR using the authenticated repository-owner GitHub session. Do this before waiting on checks.
- Confirm that Codex reviews the current head commit, not an earlier revision. The `**Reviewed commit:**` SHA in the Codex result must match the leading characters of `gh pr view <number> --json headRefOid --jq .headRefOid`.
- Keep monitoring the PR after requesting the follow-up. A clean exact-head review clears the protected `review` check and the workflow merges automatically; a new P0/P1 finding requires another fix, push, and `@codex review` cycle.
- Never bypass the protected review check or merge manually because a follow-up is missing or slow. If Codex does not react to the exact trigger, report the connector failure rather than treating the content as validated.
